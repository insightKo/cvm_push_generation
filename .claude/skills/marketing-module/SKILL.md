# Marketing Module — база знаний CRO/маркетинга/бренда (Дикси-ритейл)

## Когда применять
- Проектирование новой акции / контентной кампании
- Ревью «есть ли в этой акции смысл для клиента»
- Подбор механики под цель (рост чека / частоты / возврат)
- Объяснение себе и пользователю, почему механика не сработает

> Сетка/частота/конфликты → [[email-marketing]].
> Тексты → [[hook-generator]] / [[beautiful-prose]] / [[voice-builder-dixy]].

## 0. ОБЯЗАТЕЛЬНЫЙ ПЕРВЫЙ ШАГ: прогноз → подход

Любой запрос на акцию, выборку, механику или сетку начинается **не с решения, а с прогноза**. Пока прогноза нет — не писать SQL, не генерировать тексты, не менять логику отбора.

### 0.1 Сначала прогноз

Считать на исторических аналогах ([forecast.py](forecast.py) — `build_analogue_db` + `forecast_row` по факту из CVM offline), а не на глазок:

| Что прогнозируем | Как |
|---|---|
| **Количество клиентов** | сколько попадёт в КАЖДУЮ выборку/ступень — сначала считающим запросом (без INSERT), показать цифры и согласовать |
| Отклик | % активаций/покупок из аналогов той же группы (механика × сегмент × ширина категории) |
| Доп. ТО | отклик × средний чек группы |
| **Стоимость выгоды** | охват × отклик × размер выгоды (скидка/бонусы в рублях) |
| **Маржа** | доп. ТО × маржинальность категории − стоимость выгоды; отдельно P&L на клиента |
| Каннибализация | какая доля отклика пришла бы и без акции (клиент и так покупает категорию) |

Если данных для прогноза нет — сказать, каких именно не хватает, и **спросить**, а не подставлять правдоподобные числа ([[feedback_no_fact_invention]]).

### 0.2 Потом предложить подход

Показать пользователю **варианты решения задачи** с плюсами/минусами и рекомендацией — и дождаться выбора. Особенно когда решение затрагивает:

- логику отбора клиентов (по рангу / по значению метрики / по порогу);
- разбиение аудитории между акциями одной серии;
- размер выгоды и порог чека;
- исключения и пересечения между акциями.

Нельзя молча выбрать подход за пользователя и «просто сделать» — даже если вариант кажется очевидным. Сделать без согласования можно только механическую часть (сборка файла по уже утверждённому подходу).

**Порядок всегда: прогноз (в т.ч. число клиентов) → подход на выбор → согласование → только потом пишется скрипт.**

Нельзя править логику отбора в файле до согласования — даже черновиком, даже «чтобы показать». Сначала цифры и варианты в чате, потом правка.

## 1. Цели CVM ↔ механика ↔ сегмент

| Цель | Механика | Кому |
|---|---|---|
| Рост частоты | Каскад «за N-ю покупку», бонусы за визит | Активные / Новые |
| Рост чека | Бандл, прогр. кешбэк, СТМ-Premium | Только Активные ([[feedback_big_check_segments]]) |
| Реактивация | Велкам-бонус, прощённая скидка, «вернись» | Спящие / Отток |
| Конверсия в категорию | Купон на категорию, скидка на первую покупку | По истории покупок смежной |
| Удержание | Регулярный сервис (баланс баллов, статус) | Все активные |

## 2. Воспринимаемая выгода (как клиент считает)

Клиент НЕ считает % от цены. Клиент считает **рубли** или **«хватит на X».**

❌ `Минус 5% на кофе` (для пачки 200₽ — это 10₽, не стоит внимания)
✅ `Кофе за 199₽ вместо 249₽` (50₽ экономии, ясно)
✅ `2 пачки кофе по цене 1` (ясно, что 250₽ остаются в кармане)

**Порог восприятия скидки:**
- < 10% — не работает почти ни на чём
- 10-19% — работает только если категория частая и чек большой
- 20-30% — рабочий диапазон
- > 30% — рабочий, но воспринимается как «уценка», смотри что не убьёт маржу

## 3. CRO-чеклист для акции

- [ ] **Цель чёткая.** Знаем, что измеряем (рост частоты / чек / возврат).
- [ ] **Механика ↔ сегмент совпадают** ([[feedback_big_check_segments]], [[feedback_frequency_promos_segments]]).
- [ ] **Категория ↔ сегмент совпадают** ([[feedback_segment_match_category]]).
- [ ] **Выгода ≥ 20%** или сформулирована в рублях.
- [ ] **Условие активации ≤ 1 шаг.** «Покажи купон» — ОК. «Введи код + добавь товар + минимум чек + только в будни» — не сработает.
- [ ] **Дедлайн есть.** Без дедлайна купон откладывается на «потом» и сгорает.
- [ ] **Нет конфликта с соседней неделей** ([[feedback_no_overlap_same_mechanic]]).
- [ ] **Тексты прошли** [[voice-builder-dixy]] + [[humanizer]].

## 4. Типовые ошибки ритейл-акций

1. **«Скидка на всё» без таргетинга** — каннибализация маржи, клиент бы и так пришёл.
2. **Слишком сложная механика** — «за чек от 1500₽ + 3 SKU категории X + код в приложении» — выполнят 2%.
3. **Дублирование внутри недели** — клиент получает 3 пуша «минус 20% на курицу/рыбу/мясо» от одной сети — CTR падает на всём ([[feedback_no_overlap_same_mechanic]]).
4. **Монетная акция в конце месяца** — монеты не успеют сгореть ([[feedback_coin_promos_timing]]).
5. **Большой чек на Спящих** — они не вернутся за бандлом, им нужен повод вообще зайти ([[feedback_big_check_segments]]).
6. **Узкая категория на «все сегменты»** — детское пюре всем подряд (даже без детей) → жалобы, отписки ([[feedback_segment_match_category]]).
7. **Выдуманные факты** в текстах — «дешевле, чем у Х5», «лучшая СТМ-линейка» без данных ([[feedback_no_fact_invention]]).

## 5. Брендовая дисциплина

- Дикси — **районный магазин у дома**, тёплый/конкретный/бодрый ([[voice-builder-dixy]]).
- Не лезть в премиум-позиционирование (это не Азбука Вкуса).
- Не лезть в дискаунтер-позиционирование (это не Светофор).
- В центре — **бытовое удобство и понятная выгода**, не «эмоция от шопинга».
