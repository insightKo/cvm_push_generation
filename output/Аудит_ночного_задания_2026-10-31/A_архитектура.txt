1.2. Причины (каждая подтверждена кодом):
  а) Одна последовательная цепочка. Все 39 шагов идут друг за другом, хотя половине из них не нужен ни CVM_CONTACT, ни
     друг друга (раздел 2). Редакция Standard ограничивает пакетный режим колоночных запросов двумя потоками на запрос,
     пул буферов — 128 ГБ, кэш колоночных сегментов — 32 ГБ. Поэтому один тяжёлый запрос не занимает весь сервер, и
     параллельные ветки дали бы прирост. Сколько ядер на сервере, в выгрузке нет (Q5).
  б) Полные пересчёты всей истории каждую ночь:
     - CVM_CONTACT: 4 прохода по I_CHECKHEADER 1,77 млрд строк (стр. 42, 332, 403, 448);
     - CVM_CONTACT_DATA_W: на каждый снимок проходы DATA ≤ @act_date (стр. 71, 189, 261, 283);
     - cont_price_segment: вся I_CONT_ASSORT_W, 642 млн строк, с ROW_NUMBER (стр. 30–36);
     - for_i_segment: вся история (стр. 34–35).
  в) Окна, которые по смыслу недельные, пересчитываются ежедневно:
     - clusters — новое 13-недельное окно и 39 недель календарных миссий каждую ночь, по двум организациям
       (стр. 190, 222–237, 265–266);
     - cluster_score и product_score_region — 6 недель;
     - cont_price_segment — 8 последних недель клиента.
  г) Перезалив 10 дней. Все оконные витрины ежедневно пересчитывают 10 дней:
     - client_item — дни из service.loading_log (стр. 85–118);
     - disc_model_mart — today−10 (стр. 165);
     - discount_mart — стр. 124;
     - delivery_report — стр. 22;
     - CVM_EFFECT_TODAY — акции, у которых финиш + 4 попадает в окно (стр. 413–428).
     Кроме того, шаг 1 MCI (clear_data_update, дамп 07.10) стирает:
     - недели ≥ недели начала перезалива в I_ASSORT_WEEK, I_CH_INDEXES, I_CONT_ASSORT_W, I_CATEGORY_WEEK_FOR,
       I_SHOP_WEEK;

     - в дни 1–10 — весь прошлый месяц в месячных витринах (I_ASSORT_MONTH, I_CONT_ASSORT_M, I_LFL_*, I_SEGMENT,
       I_REPORT, I_COHORT_NEW, I_TREND*, I_CHECK_MISSION, I_MISSION_REPORT, churn).

-- Q1. Длительность шагов по дням за 90 дней: дни 1–10, первые пятницы, дни недели; плюс Reload MCI
SELECT j.name, h.run_date, h.step_id, h.step_name, start_hhmmss = h.run_time,
       dur_min = ((h.run_duration / 10000) * 3600 + (h.run_duration / 100 % 100) * 60 + h.run_duration % 100) / 60.0,
       h.run_status
FROM msdb.dbo.sysjobhistory AS h WITH (NOLOCK)
JOIN msdb.dbo.sysjobs AS j WITH (NOLOCK) ON j.job_id = h.job_id
WHERE j.name IN (N'MCI Regular update', N'MCI Reload every day')
  AND h.run_date >= CONVERT(int, CONVERT(char(8), DATEADD(day, -90, GETDATE()), 112))
ORDER BY j.name, h.run_date, h.step_id;

-- Q2. Обрывается ли эффект в 18:00 (сообщения шага 52)
SELECT TOP (20) h.run_date, h.run_time, h.run_duration, h.message
FROM msdb.dbo.sysjobhistory AS h WITH (NOLOCK)
JOIN msdb.dbo.sysjobs AS j WITH (NOLOCK) ON j.job_id = h.job_id
WHERE j.name = N'MCI Regular update' AND h.step_name = N'CVM_EFFECT_TODAY'
ORDER BY h.instance_id DESC;

-- Q3. Процедуры: время против CPU (cores_avg — сколько ядер в среднем занято)
SELECT proc_name = OBJECT_NAME(ps.object_id, ps.database_id), ps.cached_time, ps.last_execution_time, ps.execution_count,
       last_elapsed_min = ps.last_elapsed_time / 60000000.0, last_cpu_min = ps.last_worker_time / 60000000.0,
       cores_avg = CAST(ps.last_worker_time AS float) / NULLIF(ps.last_elapsed_time, 0),
       ps.last_logical_reads, ps.last_physical_reads
FROM sys.dm_exec_procedure_stats AS ps WITH (NOLOCK)
WHERE ps.database_id = DB_ID(N'mci_model')
ORDER BY ps.last_elapsed_time DESC;

-- Q4. Самые долгие операторы внутри тяжёлых процедур: на какой блок уходят 1:50 CVM_CONTACT и 1:49 clusters
SELECT TOP (80) proc_name = OBJECT_NAME(st.objectid, st.dbid),
       stmt = SUBSTRING(st.text, qs.statement_start_offset / 2 + 1, 160),
       qs.execution_count, last_elapsed_min = qs.last_elapsed_time / 60000000.0,
       last_cpu_min = qs.last_worker_time / 60000000.0, qs.last_dop, qs.last_rows,
       qs.last_grant_kb, qs.last_spills, qs.last_physical_reads
FROM sys.dm_exec_query_stats AS qs WITH (NOLOCK)
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
WHERE st.dbid = DB_ID(N'mci_model')
  AND OBJECT_NAME(st.objectid, st.dbid) IN (N'CVM_CONTACT', N'clusters', N'client_item_load', N'client_item_keys_day',
        N'disc_model_mart', N'trends', N'cont_price_segment', N'CVM_CONTACT_DATA_W', N'CVM_EFFECT_TODAY',
        N'assort_week', N'cluster_score', N'delivery_report')
ORDER BY qs.last_elapsed_time DESC;
-- и включён ли Query Store (если да — история по операторам за много ночей):
SELECT actual_state_desc, current_storage_size_mb, max_storage_size_mb FROM mci_model.sys.database_query_store_options;

-- Q5. Ядра, память, редакция: нужно для решения о параллельных ветках
SELECT cpu_count, hyperthread_ratio, socket_count, cores_per_socket, scheduler_count,
       ram_gb = physical_memory_kb / 1048576, target_gb = committed_target_kb / 1048576
FROM sys.dm_os_sys_info WITH (NOLOCK);
SELECT online_schedulers = COUNT(*) FROM sys.dm_os_schedulers WITH (NOLOCK) WHERE status = N'VISIBLE ONLINE';
SELECT edition = SERVERPROPERTY('Edition'), cu = SERVERPROPERTY('ProductUpdateLevel');

-- Q6. Чего ждут шаги: снять во время шага 21 (~10:30) и шага 37 (~15:00), дважды с интервалом 10 мин;
--     сравнивать разницу снимков
SELECT TOP (15) wait_type, wait_time_ms, signal_wait_time_ms, waiting_tasks_count
FROM sys.dm_os_wait_stats WITH (NOLOCK)
WHERE wait_type NOT IN (N'SLEEP_TASK', N'LAZYWRITER_SLEEP', N'SQLTRACE_INCREMENTAL_FLUSH_SLEEP', N'XE_TIMER_EVENT',

-- Q13. Уникальность I_CONTACT и I_ORGANIZATION — условие тождества LTV при переносе из #for_cg в #first_purch
SELECT table_name = OBJECT_NAME(i.object_id), i.name, i.type_desc, i.is_unique, i.is_primary_key,
       cols = STRING_AGG(c.name, N', ') WITHIN GROUP (ORDER BY ic.key_ordinal)
FROM sys.indexes AS i WITH (NOLOCK)
JOIN sys.index_columns AS ic WITH (NOLOCK) ON ic.object_id = i.object_id AND ic.index_id = i.index_id AND ic.key_ordinal > 0
JOIN sys.columns AS c WITH (NOLOCK) ON c.object_id = ic.object_id AND c.column_id = ic.column_id
WHERE i.object_id IN (OBJECT_ID(N'dbo.I_CONTACT'), OBJECT_ID(N'dbo.I_ORGANIZATION'))
GROUP BY i.object_id, i.name, i.type_desc, i.is_unique, i.is_primary_key;
