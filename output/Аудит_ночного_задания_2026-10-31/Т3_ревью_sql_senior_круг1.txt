1. [ВЫСОКАЯ, риск зависания шага] load 185–192, keys 87–92: IF … AND NOT EXISTS (… EXCEPT …).
   Что не так: EXISTS ставит оптимизатору цель «1 строка». В ожидаемом случае (день не изменился) разница пустая и
   анти-соединение обязано пройти все 6,8 млн (товары) / 20 млн (ключи) строк, а план строится в расчёте на ранний выход.
   Дешёвым при такой цели выглядит вложенный цикл: на каждую строку порции — скан колоночной секции дня (поиска по
   колоночному индексу нет). Если оптимизатор его выберет — 6,8 млн × скан секции, шаг не закончится. Кроме того,
   «AND» в IF не гарантирует, что EXCEPT не выполнится при неравных счётчиках.
   Исправление (результат тот же):
       IF @n_new > 0 AND @n_new = @n_old
       BEGIN
           SELECT @diff = COUNT_BIG(*)
           FROM (SELECT ID_ORGANIZATION, ID_CONTACT, ID_CHECK, ID_PRODUCT, SUMMA, QTY, EXT5 FROM #chunk WHERE DATA = @d
                 EXCEPT
                 SELECT ID_ORGANIZATION, ID_CONTACT, ID_CHECK, ID_PRODUCT, SUMMA, QTY, ID_CATEGORY_5_EXT
                 FROM dbo.I_CLIENT_ITEM_DAY WITH (NOLOCK)
                 WHERE DATA = @d AND ID_COMPANY = @idc AND ID_CATEGORY_CVM IS NULL) AS x
           OPTION (RECOMPILE);
           IF @diff = 0 SET @same = 1;
       END
   В keys — так же (вложенный IF по @k_new = @k_old, внутри COUNT_BIG по EXCEPT с OPTION (RECOMPILE), @kept = 1 при 0).
   COUNT_BIG без цели «1 строка» → хеш-соединение по полным наборам; RECOMPILE → настоящий @d, отсечение секции и грант
   памяти под объём дня (в load @d — локальная переменная, оценка по средней плотности DATA за всю историю).
   Перед выкладкой: оценочный план (без выполнения) — Hash Match (Left Anti Semi Join), без Nested Loops.

- Точность сравнения товаров: строки порции уникальны по (организация, клиент, чек, товар) — GROUP BY в #chunk; EXT5 —
  функция товара (#prod — одна строка на товар). Равенство числа строк по всей секции дня (без фильтра компании) +
  пустой EXCEPT порция → (компания 1, ID_CATEGORY_CVM IS NULL) ⇒ в секции нет чужих компаний, заполненной категории
  CVM и дублей, и секция равна порции по всем колонкам (DATA — по секции, ID_COMPANY и ID_CATEGORY_CVM — через
  равенство счётчиков). NULL в EXCEPT считаются равными (SUMMA, QTY, EXT5). Типы #chunk = типам DAY, округление до
  decimal(18,2)/(18,3) происходит при вставке в #chunk, поэтому сравнивается ровно то, что вставила бы перезапись.
- Точность ключей: запрос в #kd_new совпадает с прежним INSERT (KEY_TYPE tinyint, ID_KEY bigint во всех ветках,

  параллельном плане). Строки уникальны по (организация, клиент, тип, ключ) — то же доказательство через счётчик всей
  секции. Порядок вставки ORDER BY KEY_TYPE, ID_KEY с MAXDOP 1 сохранён (порядок внутри «ничьих» — только физика).
