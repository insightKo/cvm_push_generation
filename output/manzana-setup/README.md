# Заведение в Manzana обходным путём (списки, коммуникация, условия акции)

Задача Елены 20.10.2026: то, что на стороне ДИКСИ делает агент Михаила Панова программой «Dixy CRM Tools»
(архив `Dixy CRM Tools.zip`: расширение Chrome + Python Native Host 0.74.21 и хендовер от 12.10.2026), делать на нашей
стороне под нашей отдельной учёткой робота:

1. **список CRM_GUID** из нашей базы списков → маркетинговый список в Manzana Campaign, итог — в базу списков;
2. **коммуникация** — кампания и сообщения PUSH в Manzana Campaign;
3. **условия акции** — инфокупон и механика в Manzana Online / Loyalty Admin — после согласования условий из «CVM offline».

**Всё берётся из нашего Postgres** (решение Елены 20.10.2026: первоисточник — портал; гонять списки через свой же SFTP
незачем; в Google — только уведомления): акции и сообщения — база портала (`cvm.promo`, `cvm.push`), списки — база
списков `cvm_lists` (`lists.promo`, `lists.offer_chunk`), итог заведения (список, кампании PUSH, инфокупон) — таблица
`lists.manzana` той же базы. SFTP-обмен робот не читает и не пишет, файлов и квитанций у него нет.

Обходной путь рядом с работающим процессом, ничего из него не меняется: заливка таблицы (`cvm-sheets-sync`), согласование
в портале, скрипты выборок через обменник MCI, задание списков `cvm-campaign-lists` и SFTP-обмен для ДИКСИ остаются как есть
(Елена 20.10.2026: «все как клали, так и кладём»).

В базе списков сейчас только списки портала (номера 500000+); списки скриптов выборок (101xxx) есть только в `mci_model`.
Пока их нет в базе списков, кампании таких акций ждут (`waiting_list`).
Включать заведение будет раздел «Планирование» портала (решение Елены); до этого задание выключено
(`MANZANA_SETUP_ENABLED=0`) и умеет только проверять настройки и показывать очередь.

Код ДИКСИ в наш инструмент **не копируется** (запрет авторежима агента на встраивание чужого кода; Елена может сделать
это сама — см. «Осталось человеку»): по разбору их исходников 20.10.2026 те же вызовы и защиты написаны заново здесь.
Хендовер ДИКСИ просит не запускать их программу против рабочих систем без согласования — включение робота только по слову
Елены после договорённости с ДИКСИ.

## Что известно из архива ДИКСИ (разбор 20.10.2026)

* Manzana Campaign: веб-приложение `https://campaign.manzanagroup.ru`, его API `https://apicampaign.manzanagroup.ru/v1/dixy`
  (JSON). Приложение шлёт в API заголовки `auth` / `authorization` (в разделе Loyalty ещё `groupingid`); программа ДИКСИ
  подсматривает их у запросов приложения в открытой вкладке и вызывает API с cookies браузера; сессия 4 часа.
  «Manzana Online» в их программе — раздел Loyalty того же приложения (API `/mlp/ml/*`, профиль `manzana_loyalty`),
  плюс отдельная админка ДИКСИ для инфокупонов в мобильном приложении — `https://loyalty-admin.dixy.ru` (ActiveAdmin, HTML-формы).
* Импорт списка (`lib/sftp_exchange/campaign_import.py`): `POST /mlist/exist {Name, LoadType: 4, mListMode: 3}` →
  `GET /import/s3url?key=<МС>.zip` → `PUT` архива по временной ссылке хранилища `dixy-mlistimport.hb.bizmrg.com` →
  `PUT /import/s3import {key, importType: contact_id, loadType: 4, destination: camp|campml, nameMList, mListMode: 3, sendToMO}`
  (ровно один раз, после write-ahead в реестр) → `POST /import/lists/status/<ID>` до `Processing=false`,
  `SavedToClickhouse=true`, целое `LoadedMembersCamp` → квитанция `.ok.json` (`campaign_name` = название МС «<номер>_<title>»).
* Их валидатор списка принимает только строки-GUID: **пустая строка в CSV делает весь файл невалидным** (`.error.json`).
  Наш `export.py` пишет пустую строку при пустом CRM_GUID — такие файлы ДИКСИ не загрузит (вопрос Елене).
* PUSH (`setup_push`): шаблон `GET /msgtemplates/new/5` → `POST /msgtemplates/save` (три платформы, deeplink при `dixyapp://`)
  → копия заготовки кампании `GET /camps/templates/copy/<SID>` (заготовки ДИКСИ на 1/2/3 блока, с КГ и без) → имена МС через
  `POST /segments/reflist` → дерево сегмента (`POST /segments` → `/segments/count` → `/segments` → `GET /segments/get`:
  разрешение PUSH, не удалён, токен IOS/ANDROID/HUAWEI, не в ГКГ, `list.list_name.false` = МС) → `POST /camps/count` →
  один `POST /camps` (ответ `success`) → `GET /camps/<sid>`. Кампания остаётся неактивной — активирует менеджер; активация
  в их коде есть отдельно (`POST /camps/status {SID, Status: 2}`). Вход в приложение программа ДИКСИ не автоматизирует
  (менеджер входит руками); на форме входа Manzana возможна проверка «я не робот» — уточнить при первом входе робота.
* Инфокупон (`setup_coupon`): правило лояльности `ChargeRuleBaseView` в разделе Loyalty (API `/mlp/ml/entity`,
  заголовок `groupingid`), заранее созданные пустые черновики «Инфокупон N» (их CRM GUID по API не читается — заполняется
  вручную), кампания лояльности `Campaign` (MechanicType 4), связи `MarketingList` Include/Exclude («Тестовая группа запуски»,
  «<ExternalId> Исключаемый»), фильтр чеков «DIXY_ВСЕ МАГАЗИНЫ», кнопка в Loyalty Admin (`POST /admin/coupon_data`, форма
  Rails с CSRF), показ тестовой группе, затем бой: `DateFrom`, `FilterByContactListsType`, Include = МС «<номер>_<title>».
  Механики (`activate_discount_item_filter` и др.) — те же сущности MLP (ChargeRuleBaseView + ChequeItemFilter по подгруппам
  или голд-кодам, SchedulerTask для монет). Это самый большой кусок; в роботе пока не реализован.
* Сценарии: 36 (`native_host/scenarios/catalog.py`); входы — листы Google «Медиаплан коммуникаций» и «Купоны».

## Как работает

```
cvm_lists (база списков)                                   Manzana (учётка робота)
lists.promo: campaign_name, старт ≥ сегодня,    ──►        Campaign API: /mlist/exist → s3url → s3import → status
  нет итога done; lists.offer_chunk: ЦГ                    (архив собирается в памяти)
cvm.promo (база портала): approved,             ──►        Campaign: шаблон + неактивная кампания на каждое сообщение
  «Настройка» = да → online; cvm.push approved             Loyalty (MLP API) + Loyalty Admin: инфокупон, тестовый показ
                                   ◄── итог done / error — lists.manzana (список, push, coupon)
```

Таймер `cvm-manzana-setup.timer` — каждые 15 минут в :07/:22/:37/:52 (через 7 минут после задания списков), прогон —
одноразовый контейнер `cvm-manzana-setup` под uid 10010. Один прогон (`robot.py --once`):

1. **Списки** (`campaign_lists.py`, `sql/lists_to_load.sql`): списки базы списков, которым нужен Campaign (имя кампании
   задано; у SLIP его нет), со стартом сегодня или позже и без итога `done` — только номера из `LISTS_PROMOS` (решение
   «2б»: остальные пока грузит ДИКСИ; пусто — ни одного). По каждому: CRM_GUID участников без КГ из `lists.offer_chunk`
   (пустые отбрасываются, повторы — один раз), число должно совпасть с `guids_send` акции (`SOURCE_MISMATCH`); имя МС —
   `campaign_name` акции (+ `LISTS_POSTFIX`), ≤ 120 знаков; `/mlist/exist` должен ответить `false`; CSV с заголовком
   `contactid` в ZIP — в памяти, на диск GUID не ложатся; загрузка в хранилище; один `s3import`; опрос статуса.
   Реестр `imports.sqlite3` в `/state` пишется до необратимого вызова: без ответа на `s3import` список получает состояние
   `uncertain`, и повторный запуск невозможен без человека; с ID импорта повтор только опрашивает статус; состав в базе
   изменился после запуска — `SOURCE_CHANGED`, второй раз не грузится. Итог — строка `list` в `lists.manzana`
   (`done`: имя МС, ID импорта, загружено; `error`: код и текст). GUID приходят из базы различными и без пустых
   (`sql/list_guids.sql`) серверным курсором и одним проходом пишутся в архив: в памяти только архив (2 млн ≈ 43 МБ).
2. **Сессия Manzana** (`manzana_session.py`): Playwright с постоянным профилем робота открывает приложение, при странице входа
   заполняет форму (логин, пароль, при необходимости код TOTP; селекторы — в `manzana.env`), читает заголовки запросов
   приложения к API (`…/msgtemplates*` — профиль campaign; `/mlp/ml/*` с `groupingid` — loyalty) и дальше вызывает API
   через контекст той же сессии (cookies).
3. **Кампании PUSH** (`campaign_push.py`) — аудитория — список акции из базы списков (`sql/list_of_promo.sql`): нет
   списка — `waiting_list`, другая дата старта — `list_date_mismatch`, Campaign не нужен — `campaign_not_needed`; список
   робота (`LISTS_PROMOS`) ещё не загружен — `waiting_list_import` (ждут, пока робот его не загрузит: при
   выключенной части `lists` или ошибке загрузки кампании таких акций стоят); имя МС — под которым робот загрузил список, иначе
   `campaign_name` акции (список грузит ДИКСИ). Итог каждого сообщения — строка `push` (item «<msg>:<дата>», SID кампании).
   Акции и сообщения — из базы портала (`sql/promos_to_setup.sql`: approved и ещё не
   начались), когда есть согласованные сообщения (`sql/pushes_of_promo.sql`) и список: каждое сообщение
   → свой шаблон и своя неактивная кампания по протоколу ДИКСИ, аудитория = наш МС, контрольная группа в Manzana не
   задаётся (она уже в списке), заготовка на 1/2/3 блока по числу CRM_GUID списка (`guids_send`), тестовые телефоны из `PUSH_TEST_RECIPIENTS`. Реестр `pushes.sqlite3` по ключу «номер:сообщение:дата»: повтор
   ничего не создаёт; без ответа на сохранение — `uncertain`, повтор запрещён. Активация — только при `PUSH_ACTIVATE=1`.
   Отметка акции `state/<номер>_<старт>.campaign.done` — когда все её сообщения сохранены; отметки живут до старта + `RETENTION_DAYS`.
4. **Инфокупон для тестового показа** (`coupon_setup.py`, `loyalty_admin.py`; `online`, только при «Настройка» = да).
   Решение Елены 20.10.2026: акцию (кампанию лояльности) и механику MCI заводит сама, робот делает только инфокупон и
   показывает его тестовой группе. Manzana Online = раздел Loyalty того же приложения Campaign (API `/mlp/ml/*`,
   заголовок `groupingid`), та же учётка робота. Протокол ДИКСИ (`setup_coupon` + `setup_coupon_button`):
   справочники по точному имени (МС «Тестовая группа запуски», фильтр чеков «DIXY_ВСЕ МАГАЗИНЫ», партнёр «DIXY PARTNER»)
   → черновик «Инфокупон N» из реестра `coupon_drafts.json` (ID правила + CRM GUID купона; GUID API не отдаёт, его
   вписывает Елена; робот занимает первый свободный) → проверка, что черновик пустой инфокупон (`IsForCoupons` нет,
   `ResultType` 1, бонус 0) → скрытое сохранение полей одним PUT (название из «Название информационного купона для МП»,
   `ExternalId` ≤ 47, описание из «Текст на информационном купоне / слип-чеке», период min(сегодня, старт) 00:00 — окончание
   23:59 МСК, показ 1 = скрыт, аудитория по спискам, кампания черновика «Информационные купоны» — как у ДИКСИ при пустой
   «Кампании», решение 20.10.2026) → связи Include тестовая группа, Exclude фильтр чеков, Exclude список «<ExternalId>
   Исключаемый» (`_ex`, создаётся один раз; для акцептного купона ещё Include «… Включаемый» `_in`; акцептный = слово
   «Активируй» в названии или тексте купона — решение 20.10.2026, позже заменится признаком из справочника механик)
   → кнопка в админке ДИКСИ `loyalty-admin.dixy.ru` (своя учётка,
   форма ActiveAdmin: GUID, текст и ссылка из «Кнопка» — ссылка до конца строки, с пробелами; пусто или «В каталог» —
   «В КАТАЛОГ» `dixyapp://app/catalog`; текст без ссылки («подборка», «нужен диплинк») — остановка `BUTTON_NO_LINK` без записи; поиск по GUID
   в полном CSV, строго как у ДИКСИ: BOM снимается, пустой/урезанный/недоступный экспорт — остановка `CSV_INCOMPLETE`,
   постраничного обхода нет; один POST, после неясного ответа — до 4 поисков по GUID) → проверка чтением → показ 3
   (с фильтрацией) → активация → проверка (связи Include/Exclude — ровно наши). Остановки без записи: занятое другим
   правилом название или `ExternalId` (`NAME_CONFLICT`); чужие связи MarketingList или ChequeFilter у черновика,
   неактивный фильтр чеков, в ответе черновика нет IsActive/IsForCoupons/ResultType/Bonus/CampaignId (`CONFLICT`);
   правило черновика уже у купона другой акции в реестре или повтор `rule_id`/GUID в `coupon_drafts.json`;
   перенос старта акции — купон уже заводился под прежним ключом (`PROMO_MOVED`, новый черновик не занимается).
   Реестр `coupons.sqlite3` по ключу «<номер>_<старт>» со стадией и текстом ошибки (без «Call log» Playwright и значений
   auth/cookie); повтор продолжает с недостающего, ничего не создаёт дважды: перед POST списка `_ex`/`_in` ставится
   отметка, и при повторе список только ищется (в том числе полным перебором без полнотекстового индекса).
   **Перевод в бой** — только по слову человека: `robot.py --publish-coupon <номер>_<ГГГГММДД> --audience "<МС>|все"`
   (старт 00:00, аудитория = наш МС по точному имени или все клиенты, активация; тестовая группа и `_ex` остаются,
   как у ДИКСИ; вход в админку купонов не нужен). Итог в реестре: `live` или `publish_failed` (в базе списков — строка
   `coupon` с item «бой»); таймер такой купон больше
   не трогает. Сбой после выключения купона — `PUBLISH_INTERRUPTED`: купон выключен, команду повторить. Идёт прогон
   таймера — команда не выполняется, код 75. Позже эту кнопку даст раздел «Планирование» портала.

   Итог тестового показа — строка `coupon` в `lists.manzana` (ID правила, GUID купона — не клиента, имя купона).

Итог в базе пишется без CRM_GUID клиентов (маскируются в любом тексте); сбой записи итога — `record_failed` в журнале,
прогон с кодом 1. Без базы списков (`LISTS_PG_PASSWORD` пуст или нет связи) купоны идут, списки и кампании ждут.

Режимы: `--check` — настройки, база портала, база списков; `--dry-run` — очередь и шаги без браузера; `--once` — выполнить
(только при `MANZANA_SETUP_ENABLED=1`). Прогон с ошибкой по любой задаче завершается с кодом 1 — служба `failed`.

## Установка

База списков — один раз, до робота (портал, `db/lists/`): положить `lists-db-patch/002_manzana.sql` рядом с
`001_lists.sql`, применить `setup.sh.patch` (строка входа `lists_manzana` из сети compose), выложить портал и на ru:
```bash
/srv/cvm_portal/app/db/lists/setup.sh
```
(повторный запуск безопасен: пароли не меняет, переписывает `pg_hba.conf` и применяет новые миграции).

Робот — с фермы (классификатор отклоняет — команду выполняет Елена):
```bash
/srv/projects/cvm_platform/tools/manzana-setup/install.sh
```
Доступы — на ru, без отображения паролей (только в терминале: скрипт без него останавливается):
```bash
ssh ru
```

## Безопасность (до `/security`)

* Данные: списки CRM_GUID робот читает из базы списков (роль `lists_manzana`: в `lists.promo` — только номер, старт, имя
  кампании, число GUID; `lists.offer_chunk`; запись — только `lists.manzana`), держит их в памяти и отправляет только в
  хранилище Campaign по временной ссылке с проверенным хостом; на диск, в журнал, реестр, итог в базе и вывод службы GUID
  не попадают (`redact`, `safe_text`, текст необработанного исключения не печатается). Хранилище SFTP-обмена роботу не
  монтируется. База портала — роль только на чтение перечисленных колонок `cvm.promo` и `cvm.push`. К MCI задание не ходит.
* Браузер открывает только `MC_URL` (`https://`); исходящие соединения: `campaign.manzanagroup.ru`,
  `apicampaign.manzanagroup.ru`, `dixy-mlistimport.hb.bizmrg.com`, `loyalty-admin.dixy.ru` (только `LOYALTY_ADMIN_URL`, `https://`).
  Профиль Chromium с сессией
  входа — 700 под uid 10010, в бэкапы не входит. Снимки экрана при ошибке — только в `failed/`, 14 дней.
* Учётка робота в Manzana — отдельная (не персональная), с правами на импорт списков, кампании и раздел Loyalty;
  пароль — `manzana.env` (600), вводится `set-secrets.sh`. Отзыв: выключить учётку в Manzana,
  `systemctl disable --now cvm-manzana-setup.timer`, `rm -rf /srv/cvm_portal/manzana/profile/*`.
* Контейнер: корень только чтение, без capabilities, `no-new-privileges`, память 2 ГБ; Chromium без SUID-песочницы
  (`--no-sandbox`) под непривилегированным uid.
* Один список в Campaign может грузить только одна сторона: ДИКСИ по-прежнему забирает наш `inbox/` своей программой,
  поэтому робот грузит только `LISTS_PROMOS`; второй импорт того же МС остановится на `/mlist/exist` («уже существует»).

## Осталось человеку

1. Учётка робота в Manzana Campaign (импорт списков, кампании, Loyalty), адрес партнёра / проекта, второй фактор — в `set-secrets.sh`.
2. Первый вход робота: открыть форму входа и уточнить селекторы (`MC_*_SELECTOR`), если стандартные не подошли.
3. Миграция базы списков `002_manzana.sql` и строка входа (`setup.sh`), `install.sh` на ru, `set-secrets.sh`;
   совместная проверка на тестовом списке портала (номер 500000+ в `LISTS_PROMOS`, тестовые кампании без отправки).
4. Если нужен именно код ДИКСИ, а не повтор протокола: скопировать `lib/` и `native_host/` из архива в `vendor/dct/`
   на ферме самой — агент этого сделать не может.
5. Учётка робота должна видеть заготовки кампаний ДИКСИ (`PUSH_BLUEPRINT_*`) и справочник сегментов; проверить на тестовой акции.
6. Инфокупоны: завести в Manzana несколько пустых правил «Инфокупон N» в кампании «Информационные купоны» и вписать их
   ID и CRM GUID в `/srv/cvm_portal/manzana-state/coupon_drafts.json` (образец в `manzana.env.example`); учётка робота
   в `loyalty-admin.dixy.ru` (`set-secrets.sh`); проверить на тестовой акции, что робот видит МС «Тестовая группа
   запуски», фильтр чеков «DIXY_ВСЕ МАГАЗИНЫ» и партнёра «DIXY PARTNER». Перевод в бой — `--publish-coupon`, позже из
   «Планирования». Акция и механика — MCI руками (решение 20.10.2026). Картинка купона — https-ссылка из колонки
   «ССЫЛКА на макет купона» (`cvm.promo.coupon_layout_url`, обычно файл Manzana `apicampaign.manzanagroup.ru/files/dixy/…`);
   колонка пуста — робот картинку не задаёт (у ДИКСИ она обязательна), её добавляют руками в Manzana в правиле купона.
